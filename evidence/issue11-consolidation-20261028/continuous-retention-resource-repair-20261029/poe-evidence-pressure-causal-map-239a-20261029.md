## Complete ownership/state chain

1. Source module validates notification/RPC evidence and calls runtime `record(kind,data)`. The runtime serializes to estimate an8MiB maximum record, creates the existing private recorder if necessary, classifies financial-durability role, then calls `nativePaperRecordServiceEvidence`.
2. Recorder `record()` rejects closed/closing, diagnostic writes after sticky fatal, insufficient real disk reserve, an oversized record, or diagnostic byte/segment exhaustion. Unexpected serialization/write/integrity exceptions set sticky fatal. Every refusal goes back to the runtime unavailable callback, setting `serviceEvidenceHealthy=false` and closing new entries; future source admission fails immediately.
3. `sourceAdmission()` requires BOTH that sticky runtime flag and current recorder candidateAdmissionAllowed, plus current process/resource/manual-marker/financial headroom. Native packet admission checks this again after recording before trades enter windows, so rejected required evidence cannot become valid qualification.
4. Main loop pressure ORs resource pressure, `!serviceEvidenceHealthy`, and recorder admission false. `quarantineSources()` captures a source checkpoint, closes new risk, stops feeds/engine, records the interruption, and schedules2/4/8/16/32/60s recovery. That failure count is not reset on each healthy generation.
5. Logical allSettled completion sets closingSettled, but recovery ALSO requires actual native/feed physicalTransportsSettled and RPC inFlight/waiting zero. It therefore does not equate cancellation with physical settlement.
6. `recoverSources()` requires current recorder admission true, resource headroom, no manual suspension/RPC fatal and expired recovery time. It rebuilds Native/Engine/Feeds, resets startup index, clears closed/recovery state and runtime evidence flag, then records recovery-ready. The recorder itself is reused, not reconstructed. Fresh subscriptions and full windows are still required.
7. Main-loop maintenance runs at most once/second and is asynchronous/singleflight. Its completion can restore recorder pressure but does not reopen already quarantined sources itself; the recovery/backoff path must run.

## Recorder state distinctions

- `pressure` is recoverable; successful diagnostic recording below headroom or completed verified maintenance may clear it.
- `fatal` is process-sticky (`CHECKPOINT_UNAVAILABLE`, `RECORD_IO_OR_INTEGRITY_FAILURE`, `FILESYSTEM_UNAVAILABLE`, `RETENTION_IO_OR_INTEGRITY_FAILURE`, `RECOVERY_CHECKPOINT_UNAVAILABLE`). `usage().pressureReason` includes fatal before ordinary pressure, and admission requires no pressure. Thus fatal CANNOT coexist with candidateAdmissionAllowed=true in a single current usage result. Financial essential records may still be attempted after fatal, but they do not clear it.
- Runtime `serviceEvidenceHealthy` may remainfalse after current recorder usage becomes healthy; successful source reconstruction is its intended reset. Constructor recording failures currently precede the final resettrue, so that reset can overwrite an unavailable latch raised during reconstruction; final recovery-ready record can latchfalse again. This is a separate containment issue, not the measured headroom cause.
- `requiresCriticalRecovery` is durable and distinct from fatal/pressure. Missing/torn essential prefixes close new risk until explicit financial-recovery evidence is durably recorded; no diagnostic eviction clears it.
- Supervisor restartRequired currently reflects RPC fatal only. A sticky recorder fatal with otherwise fresh status/healthy resources can leave candidate capture quarantined indefinitely. Never clear a genuine integrity failure blindly or call that current headroom pressure.

## Retention, pins and expensive work

- Normal records serialize/hash/parse and write synchronously on the source event loop. Runtime/module/recorder each serialize related bodies; large provider/transaction objects multiply CPU work. Essential appends fsync the data and checkpoint; checkpoints write a bounded<=1MiB state file, fsync, rename and fsync directory. Diagnostic8MiB sealing also synchronously fsyncs and persists receipts.
- Disk/path checks are synchronous and sampled no more than once/second. Constructor validates metadata for up to514closed segments, recovers/parses/hashes at most two8MiB active segments, seals them and persists restart receipts.
- Constructor resets EVERY restored sealed segment's monotonic retention start to now. This deliberately makes old history young for another300000ms. It explains the first startup pressure delay; proactive maintenance cannot evict genuinely/unprovably young segments safely. Current data lacks a cross-process monotonic age witness, so wall-clock subtraction alone is unsafe after a clock jump.
- Maintenance selects only unpinned mature closed diagnostics, streams/hash-verifies them in64KiB chunks, records eviction receipt, unlinks only the owned namespace file and checkpoints. Hashing/fsync/checkpoint remain source-process CPU/I/O work despite asynchronous reads. The singleflight pass prevents duplicate workers but the loop has no per-pass file-count budget.
- `pinRange` synchronously seals the current diagnostic segment first. It selects WHOLE8MiB segments intersecting the requested interval across all selected scopes, not only the target mint. Async copying/hashing can therefore amplify a small60s candidate proof into many MiB. Up to3recorder pins are allowed; NativePaper currently initiates at most one proof-preparation task at a time. Pins lock source files against eviction until all copies settle and reserve actual disk bytes before copying.
- Different mint/window proofIDs may copy overlapping segments again. Completed proofs and financial essential files are never diagnostic-evicted. Expired qualification deadlines do not cancel the already-running copy; later completion cannot authorize an earlier decision. Pin backlog can temporarily prevent mature eviction; retained protected bytes grow until actual disk control intervenes. Partial failed-proof copies remain retained evidence.
- All callbacks run on the same source event loop as parsing, SDK validation, deadline selection, ledger/protection, local report/checkpoint and backup preparation. Async pin/maintenance reads yield, but hashing and synchronous fsync phases still contend. Existing CPU/RSS/disk/lag checks observe this; quiet tests do not establish busy held-position bounds.

## Necessary versus optional bodies

`essential` means financial-durability role, NOT whether information is necessary for qualification. Required executed `native-flow-validated-events`, notification identities, independent audit raw pages and support context can live in the rolling diagnostic namespace until qualification pins them. They must not be sampled. Representative raw-log samples, repeated dispatch state, redundant source/usage summaries and exact duplicate origin-proof bodies are possible compression/coalescing candidates only after their independent retained reference/completeness role is established. Existing dispatch-state coalescing already limits16transitions per target; do not count it as a new saving.

239a telemetry provides aggregate retained bytes, refusals and pressure, not per-kind encoded-byte/record counts or file-verification latency. Immediately before first shutdown,125170877→125859420B in15.019s is~45.85kB/s aggregate growth. It does NOT prove which class dominates, original event rate, historical oldest-segment age, or whole-market coverage.

## Coherent narrow correction recommendation

Keep the128MiB cap,300s minimum retention,8MiB record/segment bound, exact hash verification, pin locks, protected proof rules and existing hard120MiB admission stop. Add proactive low-water maintenance while the recorder is healthy: trigger by112MiB (cap-minus-two-segments), retire only verified mature/unpinned segments toward104MiB (cap-minus-three-segments), using existing singleflight worker and bounded/yielding passes. This provides8MiB async runway before hard admission and16MiB hysteresis after successful work. At the measured~45.85kB/s growth, one8MiB runway is~183s, substantially longer than an expected local8MiB verification—but actual EC2 verification/hash/fsync latency and peak encoded bursts must be measured before claiming the envelope.

Do not mask hard pressure or continue unaccounted recording. If all files are young/pinned, disk reserve is real, or verification cannot keep pace, preserve the hard stop and explicit unusable windows. Tests must include mature healthy crossings without quarantine, young/pinned controls still stopping, overlapping pins, busy writes during delayed verification, hash/I/O failures, restart aging, and retention/proof completeness. A bounded forward interval must verify multiple mature watermark crossings,0avoidable source-generation resets and actual resource use.

The startup rejuvenation gap remains separately characterized. The safest later age fix is a durable same-boot monotonic witness (validated boot ID + system monotonic seal time) with conservative fallback for old/missing/different-boot records; wall time alone cannot safely distinguish elapsed time from a forward clock jump. A temporary recovery cohort would need an explicit bounded global disk budget and prevents arbitrary extra capacity claims; simply raising128MiB or shortening300s to match one sample does not fix the recurring maintenance-order defect.
