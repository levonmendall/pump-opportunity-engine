## What information the decision actually consumes

| Responsibility | Necessary information | Information that does not establish it |
| --- | --- | --- |
| Frozen feature-only persistent-buying assessment | Six complete closed 10-second buckets; actual executed ordinary buy/sell amounts; trader-role wallet; exact deduplicable event identity; confirmed availability; corrections/gaps; net buying, positive buckets, distinct buying wallets, largest-wallet share, first/last observed trade ratios | Failed transactions are not executed trades. Wallet count is not a count of independent people. Indicative price movement does not establish executable profit. |
| Market eligibility | Canonical supported pool/mint and verified on-chain migration time, evaluated against the actual strategy age limits | Listener receipt time, token creation time, and token name are not migration time or canonical pool proof. |
| Executable entry | Correctly sized current quote, supported pool/mint/vault/configuration/fee state, coherent source context, required slot floors, modeled execution costs, risk permission | Feature-only `not-rejected` is explicitly not qualification. No extra quote is needed to compute that feature-only result. |
| Held-position exits | Actual-size net liquidation value, cost basis, current time, quote validity, own pending actions and financial state | The current stop/take-profit/time exits do not use other traders' transaction flow. Excluding held-token enrichment is already part of the design and is not a new saving. |
| Independent completeness/integrity | Independently bounded history, observed/absent signatures, relevant successful transaction classification, commitment/status agreement, genuine notification availability and slot fences | An open socket, an ACK, two agreeing feeds, or a raw message count does not prove complete executed flow. |
| Reproducibility/diagnostics | Source/configuration identities, exact receipt/validation/dispatch timings, bounded payload evidence and usage | Every diagnostic field is not itself a predictive input. Removing fields after delivery does not save wire traffic or physical requests already made. |

`src/strategy.ts` freezes the current predictive requirements at net buying >= 1 SOL, >= 4 positive buckets, >= 5 buyer wallets, largest buying wallet <= 35%, and nonnegative observed trade-price return. The version name retains the historical `unfrozen` suffix, but this run's executable/configuration is frozen. `assessPredictiveBuying` returns only `failed`, `unavailable`, or `not-rejected`, always `qualified:false`.

The native contract accepts real program-log position identities (`signature`, program, log index, frame ordinal). It does not require invented compiled-instruction indices. Integer amounts, actual trader roles and known event semantics remain required. This native authority contract must not be misreported as an independent full-SPL-transfer cross-check: current assessment records explicitly mark that cross-check unavailable.

## A demonstrably stronger requirement than executed-flow completeness

`src/native-flow-audit.ts:61` includes successful, failed and nontrade captured notifications in `requiredSignatures`. At lines 94-95, **every** independent strict-interior pool-address history row absent from the notification ledger makes the window unusable, without filtering `success`. `test/native-flow-audit.test.ts:26` explicitly asserts this for both a successful and a failed missing transaction. This is an intentional packet-census requirement in current code, not evidence that every such row contains a swap.

An independently confirmed failed transaction has no committed AMM swap effects. Requiring its WebSocket packet cannot change the frozen executed-buying features. A narrowly tested distinction between **complete executed strategy flow** and **complete delivery of all pool-address packets** could therefore avoid false economic incompleteness from missing, independently failed rows. Preserve the failed row, its status, the original packet-loss diagnostic, commitment/reorg handling and all usage accounting. A failed/success status disagreement must remain blocking. This is a proposed refinement, not an applied or runtime-verified repair.

This does **not** permit ignoring missing successful rows: signature history does not say whether a successful transaction contains a relevant swap, routed/multiple swaps, protocol effects, or no relevant trade. A bounded targeted reconstruction could classify only missing successful rows. Proven nontrade rows could potentially resolve the economic completeness question before the original decision deadline; discovered relevant late trades must leave the earlier window unusable, never be backdated. Such reconstruction has real request/latency cost and requires a separate test. Historical successful late-notification failures would not be fixed by the failed-row distinction.

History RPC pages still contain failed/nontrade rows, so this refinement alone does not eliminate those page requests. It can reduce unnecessary window invalidation, not automatically bandwidth or history scanning cost.

## Boundaries that remain necessary, and policy that can be optimized

* **Information availability:** `receivedAt` and complete validation availability are separate. Confirmed information admitted late cannot become an earlier decision input. The five-second event admission deadline and ten-second decision bucket are current service policies; relaxing either changes the tested timing behavior, not just storage efficiency.
* **Slot fences:** independent history is a conservative strict-interior slot census. Slots are not application-availability timestamps. A lower fence behind the WebSocket's served state can include transactions outside the useful receipt-time target. Current code already prefers a valid actual prewindow notification over a looser context fence. Further narrowing needs evidence of the real boundary, not block-time interpolation or dropping inconvenient rows. Bank Clock evidence remains distinct from `getBlockTime`.
* **Paging and scheduling:** current resumable audit has at most four 1000-row pages, one physical page per step, 1500 ms physical timeout, 2000 ms operation admission bound and an original-bucket deadline. Exhaustion, missing boundary coverage, no dispatch runway or a late result can produce an unavailable audit without proving missing trade data. Trace evidence is needed before changing these controls. They cannot simply be raised while assuming provider entitlement or weakening holding protection.
* **Whole-log validation:** `pilot-native-flow.ts` parses the complete bounded AMM invocation stack of a successful notification against known fresh scopes. Unknown protocol/frame semantics can conceal actual executed amounts or effects, including cross-pool transactions; ignoring them is not an equivalent optimization. Known non-buying protocol effects may be decoded separately, but never counted as ordinary buyers or buying pressure. The existing V3 path is expressly feature-only shadow observation, not financial authorization or proof of every protocol variant.
* **Corrections:** current raw hash/slot changes invalidate affected candidates, including economically irrelevant failed/nontrade packet changes. A semantic correction policy might avoid some unnecessary invalidations only after proving unchanged successful-trade/protocol/eligibility effects and preserving genuine reversals/status disagreements. Blindly ignoring changed raw bytes is unsafe.
* **Evidence retention:** bounded raw representative shapes are diagnostic; accepted executed event bytes and exact identities are retained independently. Metadata may be compacted after preserving the active window, slot fences and correction obligations. Removing full transaction retrieval can be equivalent only where the current proven program-event contract supplies every required field; it cannot be justified merely by sampled verification.

## What the ongoing counters can and cannot mean

`native-candidate-runner.ts:62` increments `qualityGaps` for candidate invalidation callbacks. A transport/control failure affecting six candidates can contribute six gaps; the counter is not a missing-trade count, a unique-window count, or 36 distinct information omissions.

`auditUnavailable` can represent unavailable history, rate/cooldown/operation failure, incomplete range coverage, or bounded paging/deadline limits. `finishAudit` also preserves completed audit evidence separately from admission; a technically completed result arriving after its original decision bucket is not a valid earlier predictive assessment.

The current source separately records fence warming as `deadlineEligible:false`, with no audit request. That known initial-warming classification was already corrected at the frozen source. Consequently, the ongoing 12 misses cannot be dismissed as the old warming bug without each window's lower-fence eligibility, enqueue/dispatch, physical operation and validation timeline. A genuinely eligible decision that could not complete by its declared deadline is an operational miss even if trade feature collection itself was complete.

**Conclusion:** not all collected information is a predictive input. Failed/nontrade packet census, raw representatives and some metadata serve integrity/diagnostics. The strongest source-supported equivalence candidate is to stop equating a missing independently failed pool transaction with missing executed strategy flow. Missing successful trades, unknown successful program semantics, commitment/corrections and real information-availability deadlines remain essential. None of these source findings alone identifies the causes of the ongoing run's 36-gap/9-unavailable/12-miss snapshot; attribution requires that exact run's retained per-event records.
