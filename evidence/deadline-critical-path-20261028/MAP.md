## Every identified blocking class

1. **Outer-loop work before `engine.step`.** `run-native-paper.ts:160`–179 prioritizes due financial actions and held protection, then ownership synchronization, USD refresh scheduling, backup scheduling, report/checkpoint, startup sources, executable candidate work, source work, flat housekeeping and50ms sleep. A ready audit is not independently dispatched during an awaited operation. Due financial/protection work is legitimate priority; observation must be explicitly suspended where promises cannot jointly fit.
2. **Discretionary work admitted before future eligibility is represented.** Replacement allocation is now skipped when an audit is already ready (`:205`–211), but setup already allocated during warming remains pending in native service. Origin verification can be a nine-second multi-read helper. `:235` computes `nextPredictionDeadline` only from candidates with `lastAssessmentEnd>0`; newly admitted/re-promoted candidates have zero, so an imminent first complete window is omitted. This is a concrete source-level admission blind spot; no claim that it caused a particular current forward miss without trace correlation.
3. **Fixed native-service ordering.** Required PONG/unsubscribe/support/reconnect/subscription/heartbeat share the same physical gate as history. Current source service can give setup/refresh precedence before a ready audit. Some work is essential to preserve capture, but initial setup is discretionary and needs separate feasibility/admission. An unsubscribe after valid rejection is queued, not physically free.
4. **Multiple independent deadline checks, no single horizon.** Native heartbeat/support expiry, pool-audit bucket, outer financial/cutoff and provider gates are checked in different layers. Snapshot/readiness times can change between them. A stale snapshot cannot authorize late data, but recomputation and phase changes can eliminate an assumed service opportunity.
5. **Nonpreemptible physical occupancy, cancellation and pacing.** One actual operation plus its settlement blocks all others, including HTTP and WS management. A paced operation sets `busy` before physical start. Abort does not refund a start or erase uncertainty; late settlement remains real contention. Source control/HTTP cooldowns are separate but physical ownership is shared.
6. **Provider/query availability.** History timeouts have per-pool query cooldowns (first2s, bounded escalation), and three distinct query timeouts within10s can trigger global backoff. Real429/overload/Retry-After remain global and must not be bypassed. Connection reuse is uninstrumented; no code inference proves provider saturation.
7. **Synchronous event-loop work.** Native packet parsing/normalization, callback feature updates, notification retention/compaction, hashing/cloning, HTTP body assembly/JSON/domain validation, signature history validation and evidence serialization/writeSync all share the audit/timer event loop. The helper is resumable between pages, not preemptible inside one validation pass. Each received WS chunk synchronously persists the authoritative ComponentBudget counterbook (`component-budget.ts:115`–118); HTTP chunks also persist (`:141`). Atomic saves include file and directory fsync. These preserve accounting but have unbounded-by-timer wall delay while running synchronously.
8. **Status/report/checkpoint work.** `run-native-paper.ts:153`–156 produces ledger projections/report history/trade cache, source/watch/feature snapshots, repeated usage views, status atomic write and a watch/account manifest checkpoint. Its admission considers holding/pending boundaries, not audit boundaries. The reporting budget is detected only after completion. Network publishing is independent, but status construction is not outside the market event loop. `checkpoint()` is also invoked before executable candidate work. Durable ledger writes, backup setup/worker messages, garbage collection and filesystem contention can delay the loop; exact cost needs span/profile evidence.
9. **Physical/request/resource admission.** Sixty starts/minute,20/10s,250ms spacing, one operation, source/CPU/evidence/storage/run limits and source cutoffs can make promises jointly infeasible. A larger candidate map or another queue does not create capacity. getTransaction8/10s currently applies to migration/support enrichment, not every native ordinary trade; native selected-flow validation needs zero per-transaction enrichment in this contract.
10. **Generation or evidence invalidation.** Disconnect/correction/unsupported successful instructions, retention refusal, source support expiry, retirement/age expiry, failed historical denominator and shutdown can invalidate a target while a page is in flight. These are data-availability failures, not dispatch latency, and must not be “fixed” by simply granting priority or extending a timeout.

## One coherent intervention, after trace attribution

The next repair must share one deadline model across the existing components, without adding a second queue or provider budget:

- Expose a bounded calendar containing **future first complete windows** for warming candidates as well as ready/continuing targets, native liveness/support expiry and owned financial deadlines. Use real ACK/availability phase and preserve complete-window warming.
- Admit each discretionary replacement/support preparation and nine-second origin helper only when its whole nonpreemptible chain plus cancellation/validation reserve leaves service opportunities for all already-committed deadlines. Reconsider between existing helper reads if a safe cancellation/continuation boundary exists; never claim physical work vanished.
- Keep required source controls and owned financial actions prioritized by actual deadlines; distinguish mandatory liveness/support from discretionary setup. Coalesce one coherent support refresh where its validated state serves several targets, retain actual refresh phase, and avoid repeated early preparation without progress.
- Reserve bounded per-target page opportunities with fair continuation service and measured demand, rather than a single page job that ignores peers. If complete audit demand cannot fit, explicitly reduce/suspend admission and mark lost coverage; never solve contention by silently dropping successful evidence.
- Include the next audit start/completion boundary in synchronous reporting/checkpoint/analytics admission. Make critical synchronous spans observable, then optimize only measured expensive work. Preserve durable receipt/accounting and honest information availability.
- Attribute each target to explicit outcomes: normal initial fence warming; no feasible admission; ready but no dispatch; pacing; physical occupancy/settlement; HTTP headers/body/JSON; domain validation; generation/evidence loss; or valid predictive decision. Record logical and physical times separately and retain negative evidence.

Three one-page audits already reserve6s at the declared2s bound. Add one2s support operation, one2s control and125ms postprocessing reserve and the conservative sum exceeds9,999ms before holdings. Six one-page targets alone require12s under that bound. This arithmetic is an envelope warning, **not measured provider latency or proof all those operations coincide**. A feasible policy must use actual required service calendars, enforce overload admission and state its supported burst envelope; average requests/minute alone is insufficient.
